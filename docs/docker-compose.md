# Container Infrastructure

## Overview

The MeatShop platform is fully containerized using Docker Compose.

Rather than running individual services manually, the entire application stack is orchestrated through a single Docker
Compose configuration, providing a reproducible development and deployment environment.

The infrastructure includes the application backend, data stores, and a complete observability stack, allowing the
platform to run as a self-contained environment.

# Services

## Backend

The backend application contains the complete business logic of MeatShop.

The infrastructure currently runs multiple backend instances, preparing the platform for horizontal scaling and future
load balancing.

Responsibilities include:

- Business logic
- REST APIs
- Authentication
- Business modules
- Metrics exposure
- Structured logging

---

## PostgreSQL

PostgreSQL is the primary persistence layer.

Every business module stores its data inside PostgreSQL, while Flyway manages database versioning and schema migrations.

Responsibilities include:

- Persistent storage
- Transaction management
- Relational data integrity
- Database migrations

---

## Redis

Redis provides high-speed in-memory storage.

It is primarily used for session management and application caching, reducing database load and improving response
times.

Responsibilities include:

- Session storage
- Distributed cache
- Temporary application data
- Future rate limiting support

---

## Loki

Loki centralizes application logs generated by every backend instance.

Instead of inspecting logs on individual containers, all logs are aggregated into a single searchable location.

Responsibilities include:

- Centralized logging
- Log storage
- Log querying
- Operational troubleshooting

---

## Alloy

Grafana Alloy acts as the telemetry agent for the platform.

It automatically discovers running containers, collects logs and metrics, and forwards them to the observability stack.

Responsibilities include:

- Metrics collection
- Log collection
- Service discovery
- Telemetry forwarding

---

## Prometheus

Prometheus continuously collects metrics from backend services and infrastructure components.

The collected metrics provide operational visibility into the application's health and performance.

Responsibilities include:

- Metrics storage
- Time-series database
- Performance monitoring
- Alerting foundation

---

## Node Exporter

Node Exporter exposes operating system metrics from the Docker host.

These metrics complement application metrics by providing infrastructure-level visibility.

Responsibilities include:

- CPU metrics
- Memory metrics
- Disk metrics
- Network metrics

---

## Grafana

Grafana provides a centralized dashboard for monitoring the entire platform.

It visualizes metrics from Prometheus and logs from Loki, allowing administrators to monitor system behavior from a
single interface.

Responsibilities include:

- Dashboards
- Metrics visualization
- Log exploration
- Operational monitoring

---

# Networking

All services communicate through a dedicated Docker bridge network.

Using internal DNS provided by Docker Compose, services communicate by service name rather than IP address.

This simplifies deployment while keeping the infrastructure isolated from external networks.

---

# Persistent Storage

Stateful services use Docker volumes to preserve data independently from container lifecycles.

Persistent storage is provided for:

- PostgreSQL
- Redis
- Prometheus
- Grafana
- Loki

This allows containers to be recreated without losing application data.

---

# Configuration

Runtime configuration is externalized using environment variables.

Sensitive information such as credentials and secrets is never hardcoded inside the application or Docker images.

Configuration includes:

- Database connection
- Redis settings
- JWT secrets
- Logging configuration
- Monitoring configuration
- Container ports

This approach allows the same container images to be deployed across multiple environments without modification.

---

# Startup Flow

The platform follows a controlled startup sequence.

```
PostgreSQL
      │
      ▼
Redis
      │
      ▼
Backend Instances
      │
      ▼
Monitoring Stack
```

Database readiness is validated before backend instances become available, ensuring reliable application startup.

---

# Horizontal Scalability

The infrastructure is designed to support horizontal scaling.

Backend services remain stateless, allowing additional instances to be deployed without changing application logic.

Future deployment scenarios include:

- Reverse Proxy
- Load Balancer
- Kubernetes
- Auto Scaling
- Independent Service Deployment

---

# Design Principles

The infrastructure follows several guiding principles.

- Container-first deployment
- Stateless application services
- Persistent data isolation
- Externalized configuration
- Automated service discovery
- Production-ready observability
- Infrastructure reproducibility

These principles ensure the platform remains maintainable, scalable, and portable across different environments.
